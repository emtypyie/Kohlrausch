## Safety & Security Observations (against AGENTS)

**Positive patterns to verify/keep:**
- Connection status must report actual detected hardware state (no claiming connection without handshake). README states: "device status reports whether a compatible device has been verified. Selecting a serial port alone does not connect to a device."
- Flashing disabled until identification/target validation/confirmation/progress/error/post-flash verification exist. lash --dry-run does not write firmware.
- No global input capture/arbitrary command execution/host automation without implementation+authorization. Macro preview exists; host automation not enabled in release.
- Atomic saves/recoverable backups for canonical profile/config writes.
- Validate profiles/macros at boundaries; reject unknown/malformed fields; never interpret config as code.
- Board metadata separate from user profiles; no physical remapping in ordinary editor.
- Unknown matrix identities/GPIO/diode/OLED specs explicitly unverified.

**Potential risks to audit further:**
- Storage paths: ensure all writes go to %APPDATA% (not beside exe). Check src/, packages/config-schema/ for path resolution.
- Config convergence: confirm single source of truth in Rust (no duplicate schema copies). packages/config-schema/ vs any editor state.
- Flashing flow: need full guard chain (identification → target validation → confirm → progress/error → post-flash verify). Dry-run enforcement.
- Protocol/validation: ensure strict schema validation on load/save/import.
- Firmware/host boundary: firmware changes separate from host builds.
